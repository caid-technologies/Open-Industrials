# Victory policy (victory-v1)

Policy defined before implementation for tower-defense #19: the server applies all already-paid shots in a combat pulse before checking either tower. If exactly one tower is destroyed, the opposite crew wins. If both are destroyed in that same pulse, the result is a tie. Player iteration order cannot award a winner before the other side's simultaneous shot. There is no client result command, surrender victory, score tiebreaker or posthumous shot in a later pulse.

An active pre-upgrade combat save whose tower is already destroyed is finalized at its saved simulation cursor before any further work. If both towers were already destroyed, it is a tie at that observation point; no historical destruction time is invented. Existing archived recovery/abandoned/expired sessions are preserved unchanged. Earlier receipts and history are never rewritten.

The terminal record is public and contains only its policy version, stable match-derived result ID, reason, winner slot (null for a tie), authoritative resolution time and both final tower-health values. Both players receive the same record; victory/defeat labels depend on the authenticated participant's own slot. Inventories, sensors, cargo, component IDs and account identities remain private.

Finalization cancels unfinished processing/manufacturing and robot jobs through their existing cancellation paths: unspent reservations are released, paid energy stays spent, produced material and onboard cargo remain conserved. Combat orders stop. No production, charging, movement, capture, salvage or shots resolve after the result. New mutations are rejected. Exact pre-existing command retries continue to return their original immutable receipts, which may predate the result; a fresh read restores current state.

Requires matching wire-v5 clients and SQLite schema 10. Back up the complete SQLite database and upgrade engine/client together. The schema gate preserves earlier envelopes, pins, paid work, history and receipt bytes; active games adopt victory policy on their next worker advancement. Completed physical state and the result remain unchanged across reads and restart even as transport/server clocks advance.

Verification: `npm run test:simulation` includes file-backed win/loss/tie final blows, competing connections, rollback, pre-upgrade destroyed towers, job interruption, privacy, receipt replay and post-match commands. `npm run test:victory` manufactures the launcher and every slug from real recovered/graded stock, then destroys a tower and verifies the persistent result. The paired client's `npm run test:browser:results` uses explicitly curated near-final-blow SQLite fixtures (not manufacturing evidence) to verify both participant views on desktop/mobile, consistent records, private evidence, disabled controls and hard restart/reconnect. Existing recovery/combat click-through remains a separate browser scenario; the complete create/join-to-victory browser match is covered by the paired client’s `test:browser:full`, including real recovered stock, six manufactured slugs and hard restart during combat and after completion.
